# 🏛️ 核心架构

搞懂 Hermes 的核心是怎么运转的——Agent Loop 怎么转、工具怎么调、提示词怎么拼、Gateway 怎么接。读完这篇你就知道一条消息从进来到出去，中间经过了几道工序。

> [!tip] 读完你会搞明白
> - Hermes 跟你之前用的 Chat API 有什么区别
> - 它怎么记住上下文、调工具、做多轮交互
> - Gateway 怎么把 20 多个消息平台统一成一种输入

---

## Agent Loop——循环才是本体

Hermes 不是一问一答的 Chat Completion。**它的核心是一个循环**——大模型自己决定要不要调工具、调几次、什么时候停。

```
用户输入
    │
    ▼
┌─────────────────────────────────────┐
│ 1. Prompt Assembly（提示词组装）     │
│    ├─ System Prompt（系统提示词）    │
│    ├─ Persona（角色设定）            │
│    ├─ Memory（记忆注入）             │
│    ├─ Skills（技能注入）             │
│    ├─ Context Files（上下文文件）     │
│    └─ Tool Definitions（工具定义）   │
└─────────────┬───────────────────────┘
              │
              ▼
┌─────────────────────────────────────┐
│ 2. LLM Call（调用大模型）            │
│    ├─ 发送组装好的 Prompt            │
│    ├─ 支持 tool_use / function_call   │
│    └─ 支持多轮工具调用的流式输出      │
└─────────────┬───────────────────────┘
              │
              ▼
┌─────────────────────────────────────┐
│ 3. Response Handling（响应处理）     │
│    ├─ 文本响应 → 直接输出给用户      │
│    ├─ 工具调用 → 进入 Tool Exec      │
│    └─ 两者混合 → 并行处理            │
└─────────────┬───────────────────────┘
              │
         ┌────┴────┐
         ▼         ▼
      文本响应    工具调用
                   │
                   ▼
         ┌───────────────────┐
         │ Tool Execution    │
         │ ┌───────────────┐ │
         │ │ Tool1 →       │ │
         │ │ Tool2 → 并发  │ │
         │ │ ToolN →       │ │
         │ └───────┬───────┘ │
         │         │         │
         │ ▼       ▼         │
         │ 结果注入回 LLM     │
         └─────────┬─────────┘
                   │
                   ▼
         回到第2步（循环）
                │
                ▼
         直到 LLM 只返回文本
                │
                ▼
           输出给用户 🎉
```

翻译成人话：Hermes 先把自己知道的所有东西（系统提示、记忆、技能、上下文）拼成一个超大 Prompt 扔给模型 → 模型要么回文字，要么说要调某个工具 → 如果要调工具，Hermes 就帮它跑，把结果塞回去继续问 → 直到模型觉得够了，直接回文字 → 输出给你。

这才是 Agent 和普通 Chat API 的区别：**模型自己决定要不要调工具、调几次、什么时候停**。看起来像在用电脑，实际上模型在「用 Hermes」这个操作系统。

### 循环什么时候停

| 条件 | 说明 |
|------|------|
| ✅ 模型只回文字 | 最正常的结束方式——模型觉得搞定了 |
| ⏰ 超过 50 轮工具调用 | 默认上限，大部分场景 5-10 轮就出结果了 |
| ⌛ 超过 600 秒 | 怕模型无限循环的兜底机制 |
| ✋ 你手动中断 | Ctrl+C 或者点停止 |

> [!tip] 50 轮上限我从来没踩到过
> 一般 5-10 轮就出结果了。真到了 50 轮说明可能死循环了——这时候超时兜底反而是好事。

## Tools Runtime——工具是怎么跑起来的

模型说「我要调 terminal」之后，背后发生了什么：

```
LLM 返回 tool_calls
    │
    ▼
┌─────────────────────────────┐
│ Tool Registry（工具注册中心） │
│ ├─ Built-in Tools（内置）    │
│ ├─ Plugin Tools（插件）      │
│ └─ Custom Tools（自定义）     │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│ Tool Execution              │
│ ├─ 权限检查（RABC）          │
│ ├─ 沙箱隔离（标准/严格）      │
│ ├─ 超时控制                  │
│ └─ 并发执行                   │
└──────────┬──────────────────┘
           │
           ▼
    结果注入回 LLM
```

三道关卡：

1. **Tool Registry** — 先在注册中心找到这个工具有没有注册、叫什么名字
2. **权限检查** — 当前对话上下文有没有权限调它（RABC 管这个）
3. **沙箱执行** — 根据沙箱级别决定能跑什么命令

> [!warning] 沙箱不是安全银弹
> `strict` 模式只允许白名单命令 + 拦截网络。但如果真有人铁了心搞破坏，还是考虑 Docker 隔离运行更靠谱。

### 工具从哪来

| 来源 | 说明 | 例子 |
|------|------|------|
| **Built-in** | 装完就有 | `terminal`、`read_file`、`web_search` |
| **Plugin** | 插件社区贡献 | 别人写好的工具包 |
| **MCP** | 通过 MCP 协议自动发现 | native-mcp 客户端 |

### 沙箱级别速查

| 级别 | 表现 | 适合场景 |
|------|------|---------|
| `off` | 无限制 | 自己用、信得过自己 |
| `standard` | 拦截高危命令（`rm -rf`、`dd` 等） | 半信任环境 |
| `strict` | 只白名单 + 屏蔽网络 | 对外开放的服务 |

## Prompt Assembly——每次对话前的准备工作

每次你发消息给 Hermes，它都会现场拼一个 System Prompt。不是写死的，是动态组装的：

```
系统提示词
├─ Persona（角色设定）   ← 从 ~/.hermes/config.yaml 的 persona 读
├─ Memory（记忆）        ← 从 memory provider 拉你的习惯和偏好
├─ Skills（技能）        ← 匹配当前任务的技能定义
├─ Context（上下文文件）   ← 项目根目录的 AGENTS.md / CLAUDE.md
├─ Tools（工具定义）      ← 当前启用的工具集
└─ Instructions（指令）   ← 系统行为指令
```

> [!tip] 改 persona 立刻生效
> 改完 `~/.hermes/config.yaml` 里的 persona，下一条消息就变了。每一次 Prompt Assembly 都是现场读的，没有缓存。

### 相关配置

```yaml
hermes:
  persona: |
    你是一个智能助手...
  memory:
    enabled: true
    long_term: true
  tools:
    auto_discover: true     # 自动发现项目上下文文件
```

## Gateway——消息的统一入口

Gateway 是 Hermes 的「接线总机」。不管消息从 Telegram 来、Discord 来、还是微信来，它统一收进来，转成内部格式，塞给 Agent Loop。

```
Telegram ───┐
Discord  ───┤
Slack    ───┤
微信      ───┤
飞书      ───┤
...20+ 平台 ─┤
             │
             ▼
    ┌──────────────┐
    │   Gateway    │
    │  ┌─────────┐ │
    │  │ Router  │ │
    │  └────┬────┘ │
    │       │      │
    │  ┌────▼────┐ │
    │  │ Session │ │
    │  │ Manager │ │
    │  └────┬────┘ │
    │       │      │
    │  ┌────▼────┐ │
    │  │  Auth   │ │
    │  └─────────┘ │
    └──────┬───────┘
           │
           ▼
    ┌──────────────┐
    │  Agent Loop  │
    └──────────────┘
```

Gateway 内部做了三件事：

1. **Router** — 判断消息从哪个平台来的，转成统一格式
2. **Session Manager** — 管理会话状态，同一个用户的对话串在一起
3. **Auth** — 验证消息来源是否合法

> [!tip] 只接一个平台时 Gateway 的存在感很低
> 但只要接了第二个，你就知道这东西省了多少事——不用为每个平台单独写一套消息处理逻辑。

### 配置片段

```yaml
gateway:
  telegram:
    enabled: true
    bot_token: "xxx"
  discord:
    enabled: true
    bot_token: "xxx"

  control_ui:
    enabled: true
    port: 8642

  rate_limit:
    enabled: true
    max_messages_per_minute: 30
```
